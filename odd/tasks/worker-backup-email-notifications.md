## Design decision

| Concern | Approach |
| --- | --- |
| Successful boundary | Create notification intent in the **same atomic `.sync-state.json` write** that commits a published release, after processing and `current` publication. If state commit fails, publication rolls back and no event exists. Never infer a new backup from `status: published` alone: forced bootstrap republishes the same backup on every worker restart. |
| Identity | Compare the remote file ID, size, SHA-1 and optional SHA-256, matching the orchestrator's existing `stateMatches` predicate. `releaseId` and local hash are not backup identity. A forced first successful processing while notification state is uninitialized creates the first event even when an older sync state already matches; later forced processing of the same identity does not. Disablement must not erase the delivery ledger. |
| Durable state | Keep the existing v1 schema and add an optional, strictly validated notification ledger field; the reader currently rejects extra keys, so update it to accept exactly the legacy keys or those keys plus this field. No version bump is needed for legacy state. The ledger holds only the last enqueued backup identity and monotonic enqueued/acknowledged sequence counters, plus an initialization marker if needed. Persist it in the same 0600 atomic sync-state commit, and preserve it across later sync commits and acknowledgements under the exclusive lease. A legacy state has no ledger; the first successful enabled processing initializes it and enqueues one alert even if the old backup identity matches. |
| Retry and failure | Worker sends one generic email per pending sequence after sync and on later cycles **even when sync is a no-op or fails**. Bound attempts per cycle (for example, one) so a large backlog never blocks backup work. Catch SMTP failures separately; keep the pending count, emit generic status logs, and keep backup publication/readiness independent of mail. Acknowledgement write failure leaves that sequence pending and is logged without failing the backup. |
| Backlog bound | The ledger stores no per-backup event list. Each committed, newly observed identity increments the enqueued counter once; each SMTP-accepted email increments the acknowledged counter once. Pending count is their difference. Store counters as validated canonical decimal strings and use BigInt arithmetic so practical backlog growth never overflows a JavaScript number or silently drops alerts. This is a constant number of records with logarithmic counter-byte growth, comfortably within the existing 64 KiB state-file limit for any physically realistic backlog. Never coalesce, truncate, or drop a committed alert. |
| SMTP | Add Nodemailer as a pinned production dependency, using OVH MX Plan `smtp.mail.ovh.net:465` with implicit TLS (`secure: true`) and normal certificate verification; full sender address is SMTP username. Do not implement SMTP directly or use Gmail SMTP merely because the recipient is Gmail. Inject a narrow mail sender in tests; no test opens a live SMTP connection. Set connection, greeting, DNS, and socket timeouts; disable protocol/debug logging. |
| Runtime config | `MYEXPENSES_NOTIFICATION_TO`, `MYEXPENSES_NOTIFICATION_FROM`, and `MYEXPENSES_SMTP_PASSWORD` are absent/empty together when notifications are disabled; when any is supplied, require all, validate a single mailbox per address and bounded password, and reject CR/LF/control injection with generic errors. Compose forwards these as worker-only runtime variables without production address or secret defaults. Sender is also the SMTP username. |
| Message/privacy | Fixed English subject/body, e.g. “MyExpenses backup processed”; no amount, account, filename, file ID, checksum, source path, or secret. Only SMTP acceptance of the intended single recipient counts as sent. Never log transport exceptions, addresses, server responses, or secret values. |

SMTP acceptance is **not recipient delivery**. There is an unavoidable at-least-once window: if the SMTP server accepts the message but the worker crashes before durable acknowledgement, retry can duplicate it. A deterministic `Message-ID` derived from a stable notification namespace and sequence may help correlation but cannot provide exactly-once delivery. Pending mail uses the **current** runtime recipient, not the recipient that was configured when it was enqueued; the ledger stores no addresses. Do not claim otherwise.

Notifications disabled by absent configuration create no new alerts, but preserve any prior ledger and pending count across sync commits. Re-enabling drains prior pending alerts to the then-configured recipient; it does not fabricate an additional alert for an unchanged backup that was already enqueued. If no ledger existed, the first successfully processed backup after initial enable creates the first alert.
