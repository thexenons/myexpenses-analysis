# Revisión integral del 26 de septiembre de 2026

La revisión combina exploración con CodeGraph, lectura de contratos y código,
regresiones reproducidas antes de corregir, consultas SQLite independientes,
pruebas automatizadas y navegación en Chromium. Conserva los cambios previos
del usuario en `.atl/`, `.gitignore` y `.pi/`.

## Arquitectura y funcionalidades revisadas

| Capa | Responsabilidad y flujos comprobados |
| --- | --- |
| `scripts/import-backup` | Selección de copia, límites ZIP, CRC, SQLite 189/190, preferencias y DataStore permitidos, adaptación contable, referencias y dataset versionado |
| `scripts/encrypt-dataset` y `domain/security` | Entrada privada, frase, gzip, PBKDF2/AES-GCM, autenticación del formato, límites y escritura atómica |
| `infrastructure` | Descarga bajo demanda, validación, descifrado, cancelación y almacenamiento tolerante a fallos |
| `application` y `composition` | Ensamblado, desbloqueo, estado Zustand, filtros y persistencia limitada a granularidad |
| `domain/analytics` | Normalización, fechas, comparación, filtros, contrapartidas, divisas, saldos, deudas, presupuestos y agregaciones |
| `presentation` | Navegación, ocho pantallas, filtros, gráficos, tablas, selección, exportaciones, accesibilidad, estilos y adaptación móvil |
| `scripts/sync-pcloud` y `deploy` | OAuth, hosts permitidos, checksums, descargas, permisos, locks, workspaces, build, publicación atómica, rollback y configuración de cabeceras |
| Configuración y pruebas | Límites entre capas, estructura de componentes, TypeScript, lint, carga diferida, exclusión de datos claros y dependencia del formato de bóveda |

El flujo principal es ZIP → SQLite validada → dataset JSON → gzip y cifrado →
bóveda estática → desbloqueo explícito → normalización y filtros en memoria →
agregaciones y pantallas. No hay un backend de autenticación ni persistencia de
movimientos desde la interfaz. pCloud es una herramienta separada de preparación
y publicación de archivos estáticos.

Las pantallas ofrecen resumen y valoración, flujo real, deudas, presupuestos,
categorías, cuentas, patrones/calidad y transacciones con búsqueda, paginación,
ordenación, trazabilidad y CSV. Las series, rankings y comparaciones temporales
comparten los filtros globales; apertura y cierre mantienen su significado de
saldo completo de las cuentas seleccionadas.

Se conserva la arquitectura: dominio puro, puertos de aplicación, adaptadores
y presentación. La revisión no justifica sustituir el framework, introducir
dependencias de producción ni rediseñar la interfaz.

## Defectos corregidos

| Área | Problema y corrección |
| --- | --- |
| Seguridad de categorías | Los nombres `__proto__` y `constructor` colisionaban con propiedades heredadas. Los registros de categorías usan objetos sin prototipo. |
| Seguridad de importación | Se calculaba el hash antes de comprobar tipo y tamaño del archivo. ZIP y hash ahora usan una única lectura validada y acotada; se rechazan dispositivos, enlaces y cambios durante la lectura. |
| Protección de originales | Un alias de directorio podía hacer coincidir entrada y salida y destruir el original. Importación y cifrado comparan también las rutas reales. |
| Autobloqueo | Un evento tras suspender el navegador podía renovar una sesión ya caducada antes de ejecutarse el temporizador. La actividad comprueba primero el tiempo transcurrido. |
| Descargas | Las respuestas rechazadas por estado o cabeceras dejaban cuerpos de red pendientes. El lector se libera y la respuesta se cancela también en esos caminos de error. |
| Presupuestos | Un padre sin asignación sumaba dos veces los arrastres de sus hijos. Se agregan por separado base y arrastres. La ausencia de asignación se distingue de una asignación exacta, evitando que datos de otro periodo anulen acumulados. |
| Cuentas excluidas | El importador eliminaba sus apuntes y rompía contrapartidas y saldos. Conserva todos los apuntes canónicos. Por petición del usuario, todas las cuentas raíz participan en los análisis aunque tengan «excluir del total» activo en MyExpenses; las cuentas hijas permanecen fuera para evitar doble conteo. La normalización también aplica la regla a datasets importados anteriormente. |
| Divisas redondeadas | Un equivalente dinámico válido redondeado a cero se rechazaba por inferir una tasa cero. Conserva el importe y usa tasa desconocida; un equivalente no cero para importe nativo cero sigue siendo inválido. |
| Cuentas vacías | Una cuenta estática extranjera vacía podía carecer legítimamente de tasa. Se admite sólo cuando apertura, saldos y todos sus apuntes son cero, incluidos los anulados. |
| Presentación de divisas | El tipo dinámico mostrado dividía unidades menores sin ajustar los decimales nativos. Ahora usa unidades mayores. Tasas desconocidas aparecen como no disponibles y se exportan vacías; su procedencia no se etiqueta como identidad EUR. |
| Sin categoría | Los desgloses omitían apuntes sin categoría. Se incorporan al total, series, filtros y navegación con una selección inequívoca. |
| Navegación de categorías | Abrir movimientos desde una barra podía perder hijos incluidos en una selección exacta. La navegación conserva la selección representada; con selección por contrapartida se mantiene deshabilitada cuando no puede representarse sin ambigüedad. |
| Granularidad | La etiqueta automática usaba fechas de operación aunque la serie usase fecha de valor. Ambas consultan los mismos límites temporales. |
| Clasificación legacy | Una transferencia dependía de un nombre en español. Su tipo contable determina la clasificación. |
| Extremo temporal | Generar una serie del año 9999 intentaba avanzar a un año fuera del formato y podía entrar en bucle. Se detiene en el último periodo solicitado. |
| Rendimiento de bóveda | Se reconstruía base64 válido carácter a carácter y se creaba un ciphertext provisional innecesario. Se conserva la representación validada y la codificación nueva usa bloques acotados. |

Cada grupo tiene regresiones en las pruebas de su capa. Una revisión cruzada
adicional comprobó los cambios de cifrado, streams y protección de rutas.

## Nueva base local

Se procesó `data/myexpenses-backup-20260926-070855.zip` con `Europe/Madrid`.
Es esquema 190 y genera 39 cuentas, 81 categorías, 13.527 apuntes y 2 presupuestos.
`data/app-dataset.json` y `data/app-dataset.vault.json` quedan actualizados con
permisos `0600`, ignorados por Git. El ZIP original se conserva sin cambios.

Se verificaron 216.824 condiciones contra SQL independiente del adaptador,
incluidas las identidades de saldos y `ALL = REAL_CASH + DEBT`. La bóveda se
descifró localmente y coincidió exactamente con el JSON generado. La selección
automática de la última copia también devuelve este archivo.

La copia nueva activa «excluir del total» en las 22 cuentas de deuda: ese filtro
era la causa de las estadísticas a cero. Se recuperan las 22 cuentas y sus
3.274 apuntes en Deudas; Flujo real contiene las otras 17 cuentas y 10.253
apuntes. Se comprueban saldos, anticipos y recuperaciones no nulos, además de
regresiones con cuentas de deuda y efectivo excluidas en el origen.

La compatibilidad al abrir datasets anteriores supone que sus apuntes estén
presentes. Los artefactos antiguos que los omitían necesitan reimportar el ZIP.

Se mantuvo el modo de desarrollo previo, con frase vacía. Una build de
producción debe seguir rechazando esa bóveda: para publicar los datos reales
hay que cifrarlos con una frase privada mediante `pnpm data:encrypt`.

## Rendimiento observado

La lectura de un envelope sintético con 1 MiB de ciphertext pasó de 279 ms a
59 ms en una medición local antes/después al eliminar la reconstrucción base64.
Es una observación de Node, no una garantía de rendimiento en otros dispositivos.
Las pruebas de cifrado y descifrado cubren límites de bloque y los tres casos
de padding base64. Los parámetros criptográficos permanecen iguales.

## Verificación y límites

- Node con cobertura: 175 pruebas correctas, dos golden históricas omitidas;
  cobertura de líneas 82,65 %, ramas 77,04 % y funciones 87,79 %.
- Interfaz y dominio con Vitest: 216 pruebas correctas en 72 archivos;
  cobertura de sentencias 81,87 %, ramas 70,24 %, funciones 85,71 % y líneas
  87,36 %. Se superan los umbrales configurados.
- TypeScript y Oxlint: correctos, sin advertencias de lint.
- Build de producción: correcta con una bóveda sintética protegida. Chunk
  principal de 374,24 kB (119,99 kB gzip), con pantallas separadas.
- `pnpm audit`: cero vulnerabilidades conocidas en las 263 dependencias
  examinadas en esta ejecución.
- Chromium con la base real: ocho rutas a 1440 y 390 px, sin desbordamientos,
  errores JavaScript, peticiones externas ni infracciones detectadas por axe.
  Deudas y Resumen muestran los importes calculados para la base regenerada;
  saldo, anticipos y recuperaciones de deuda son no nulos y aparecen las
  22 cuentas.
- Chromium con la build y datos sintéticos: ocho rutas a 1440, 390 y 320 px,
  sin desbordamientos, errores JavaScript ni infracciones detectadas por axe
  para las reglas WCAG A/AA de las versiones 2.0, 2.1 y 2.2.
- Interacciones con datos sintéticos: entrada directa, desbloqueo, descarga
  bajo demanda, CSV, ordenación en URL, búsqueda vacía, filtros, fecha de
  valor, cierre del panel con Escape/restauración de foco y bloqueo manual.
- El ZIP coincide con su hash de procedencia y la bóveda descifrada coincide
  byte a byte con el dataset. Ambos archivos generados tienen permisos `0600`.

Los artefactos de navegador usan datos sintéticos y las comprobaciones privadas
sólo emiten conteos y resultados, sin capturas ni importes financieros.

Una instancia de Vite falló transitoriamente durante la revisión. Reiniciarla
resolvió el fallo; otras instancias nuevas también respondieron correctamente.
No se estableció la causa ni se alteraron dependencias para atribuirle una
corrección especulativa.

No se ha publicado una release ni conectado una cuenta pCloud real. Las pruebas
de pCloud usan transporte simulado; tampoco sustituyen la validación de nginx,
permisos y certificados en el servidor de destino. Chromium y axe no sustituyen
pruebas en Safari, Firefox, lectores de pantalla o dispositivos físicos.

Las dos pruebas golden del backup de agosto conservan su referencia histórica
y se omiten cuando el dataset local es otro. La nueva prueba SQL valida la base
de septiembre sin incorporar importes privados al repositorio.

La [auditoría de agosto](project-audit.md) y la
